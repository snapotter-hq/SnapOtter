# الترقية من 1.x إلى 2.0 {#upgrading-from-1-x-to-2-0}

كان SnapOtter 1.x يخزن كل شيء في ملف SQLite واحد ويعمل كحاوية واحدة. يستخدم SnapOtter 2.0 كلاً من PostgreSQL وRedis. يرشدك هذا الدليل إلى نقل تثبيت 1.x إلى 2.0 دون فقدان أي بيانات.

باختصار: أعد استخدام وحدة التخزين `/data` الحالية، وسيستورد 2.0 قاعدة بيانات 1.x تلقائياً عند أول تشغيل. ينتقل مستخدموك وملفاتك المحفوظة وإعداداتك ومفاتيح API وخطوط المعالجة. لا تُعدَّل قاعدة البيانات القديمة أبداً، لذا يمكنك دائماً التراجع.

::: tip ملاحظة لمستخدمي 1.x
وثق بـ SnapOtter كثير منكم منذ اليوم الأول، وقد شكّلت ملاحظاتكم هذا الإصدار. يغيّر 2.0 الكثير تحت الغطاء، وهذا الدليل موجود كي لا يكلفك الانتقال أي شيء يهمك. تنتقل حساباتك وملفاتك وإعداداتك ومفاتيح API وخطوط المعالجة، ولا تُمَسّ قاعدة بياناتك القديمة. شكراً لترقيتكم معنا.
:::

## قبل أن تبدأ: انسخ وحدة التخزين `/data` بالكامل {#before-you-start-back-up-the-whole-data-volume}

افعل ذلك أولاً، في كل مرة. انسخ احتياطياً وحدة التخزين `/data` **بأكملها**، وليس ملف `snapotter.db` فقط.

إليك سبب أهمية ذلك. يشغّل 1.x قاعدة SQLite بوضع WAL، لذا فإن الحاوية 1.x المتوقفة تترك عادةً معظم بياناتها المثبَّتة في `snapotter.db-wal` بجانب `snapotter.db` شبه الفارغ. نسخ `snapotter.db` وحده يلتقط قاعدة بيانات فارغة ويفقد كل شيء بصمت. تحمل وحدة التخزين `snapotter.db` و`snapotter.db-wal` و`snapotter.db-shm` ودليل `files/` معاً، ويجب أن تنتقل كمجموعة.

```bash
# Adjust the volume name to match yours (see "Check your volume name" below).
docker run --rm -v SnapOtter-data:/data -v "$PWD":/backup \
  alpine tar czf /backup/snapotter-1x-data.tgz -C /data .
```

## رقِّ إلى 1.17.2 أولاً {#upgrade-to-1-17-2-first}

رقِّ تثبيت 1.x إلى أحدث إصدار من 1.x (1.17.2) قبل الانتقال إلى 2.0. يتيح ذلك لـ 1.x تشغيل ترحيلات المخطط النهائية الخاصة به، بحيث يستورد 2.0 من مخطط معروف وكامل. الترقية من إصدار 1.x أقدم مباشرة إلى 2.0 غير مدعومة.

## تحقق من اسم وحدة التخزين {#check-your-volume-name}

لا يرى المستورد بياناتك إلا إذا ربطت حزمة 2.0 وحدة التخزين نفسها التي استخدمها تثبيت 1.x. أسماء وحدات تخزين Docker حساسة لحالة الأحرف، وكانت مقتطفات README الأقدم تستخدم `snapotter-data` بأحرف صغيرة بينما تستخدم ملفات Compose ‏`SnapOtter-data`. تأكد من أيهما لديك:

```bash
docker volume ls | grep -i snapotter
```

استخدم هذا الاسم بالضبط في إعدادات 2.0 لديك.

## المسار A: حاوية واحدة (الأسرع) {#path-a-single-container-quickest}

إذا كنت تشغّل SnapOtter بـ `docker run` واحد، فاستمر على ذلك. يشغّل 2.0 PostgreSQL وRedis مضمَّنتين داخل الحاوية عندما لا تضبط `DATABASE_URL` أو `REDIS_URL`، ويكتشف `/data/snapotter.db` تلقائياً ويستورده عند أول تشغيل.

```bash
docker run -d --name snapotter -p 1349:1349 \
  -v SnapOtter-data:/data \
  snapotter/snapotter:latest
```

راقب السجلات بحثاً عن سطر مثل:

```
Imported 1.x SQLite database: {"tables":{"users":2,"teams":1,...},"blobs":{"present":1,"missing":0}}
```

هذا كل شيء. سجّل الدخول ببيانات اعتمادك الحالية.

## المسار B: Compose (موصى به للإنتاج) {#path-b-compose-recommended-for-production}

تشغّل حزمة Compose في 2.0 ثلاث خدمات (التطبيق وPostgres وRedis). أعد استخدام وحدة التخزين `/data` من 1.x لخدمة التطبيق. يكتشف التطبيق `/data/snapotter.db` تلقائياً ويستورده إلى Postgres عند أول تشغيل.

```yaml
services:
  SnapOtter:
    image: snapotter/snapotter:latest
    volumes:
      - SnapOtter-data:/data          # your existing 1.x volume
      - SnapOtter-workspace:/tmp/workspace
    environment:
      - DATABASE_URL=postgres://${POSTGRES_APP_USER:-snapotter_app}:${POSTGRES_APP_PASSWORD:-snapotter_app}@postgres:5432/${POSTGRES_DB:-snapotter}
      - DATABASE_MIGRATION_URL=postgres://${POSTGRES_USER:-snapotter}:${POSTGRES_PASSWORD:-snapotter}@postgres:5432/${POSTGRES_DB:-snapotter}
      - REDIS_URL=redis://:snapotter@redis:6379
    # ...
```

إذا فضّلت الإشارة إلى قاعدة البيانات القديمة صراحةً، فاضبط `SQLITE_MIGRATE_PATH=/data/snapotter.db`. المسار الصريح يتغلب دائماً على الاكتشاف التلقائي.

## معاينة الاستيراد أولاً (اختياري) {#preview-the-import-first-optional}

لمعرفة ما سيُستورد بالضبط دون كتابة أي شيء، شغّل تشغيلاً تجريبياً على ملف قاعدة بياناتك:

```bash
pnpm --filter @snapotter/api migrate:sqlite -- /path/to/snapotter.db --dry-run
```

يطبع أعداد الصفوف لكل جدول، وعدد ملفات المكتبة المحفوظة التي وجدها على القرص، وأي حالات مهام سيوحّدها. ولا يحتاج إلى Postgres قيد التشغيل.

## ما الذي ينتقل وما الذي لا ينتقل {#what-carries-over-and-what-does-not}

ينتقل:

- المستخدمون، والقدرة على تسجيل الدخول. تبقى تجزئات كلمات المرور دون تغيير، لذا يعمل اسم المستخدم وكلمة المرور نفسهما.
- الفرق، والإعدادات (بما في ذلك هوية نسختك)، والأدوار، ومفاتيح API (تبقى تعمل)، وخطوط المعالجة المحفوظة.
- سجلات تاريخ المهام.
- مكتبة ملفاتك المحفوظة، السجلات والملفات الفعلية معاً، لأن `/data/files` محفوظ على وحدة التخزين.

لا ينتقل:

- جلسات تسجيل الدخول. يسجّل الجميع الدخول مرة واحدة بعد الترقية. بيانات الاعتماد دون تغيير، لذا هي إعادة تسجيل دخول واحدة لا أكثر.
- ملفات الإدخال والإخراج الخاصة بمهام المعالجة القديمة. كانت في مساحة عمل مؤقتة وقد زالت بحكم التصميم. وتبقى سجلات تاريخ المهام.
- علامات موافقة التحليلات لكل مستخدم من 1.x، وليس لها مكافئ في 2.0 (التحليلات في 2.0 إعداد على مستوى النسخة).

## إيقاف الاستيراد {#turning-the-import-off}

إذا كنت تريد عمداً قاعدة بيانات جديدة رغم وجود `snapotter.db` على وحدة التخزين، فاضبط `SQLITE_MIGRATE_PATH=off`.

## إذا كانت لديك بيانات بالفعل في نسخة 2.0 {#if-you-already-have-data-in-the-2-0-instance}

لا يعمل المستورد إلا على قاعدة بيانات فارغة. إذا بدأت 2.0 من جديد (وأنشأت بيانات)، ثم ربطت لاحقاً `snapotter.db` قديماً، فسيكتشفه 2.0 لكنه لن يستورده، لأن دمج مجموعتي بيانات قد يسبب تعارضاً في المعرّفات. سترى تحذيراً في السجلات. لاستيراد بيانات 1.x تحتاج إلى نسخة فارغة:

- إذا كانت نسخة 2.0 تحتوي فقط على المسؤول الافتراضي (أي أنك لم تستخدمها فعلياً)، فأوقف الحزمة، وأزل وحدة تخزين Postgres (`SnapOtter-pgdata`)، ثم شغّل من جديد مع وجود `/data` القديم. سيُستورد بنظافة. يمسح هذا فقط بيانات Postgres المؤقتة، لا قاعدة بيانات 1.x لديك.
- إذا كانت نسخة 2.0 تحتوي على بيانات حقيقية تريد الاحتفاظ بها، فلا يمكن دمج مجموعتي البيانات تلقائياً. صدّر ما تحتاجه واستورد بيانات 1.x في نشر جديد منفصل.

## التراجع {#rolling-back}

لا تعدّل الترقية `snapotter.db` الخاص بـ 1.x أو تحذفه أبداً. إذا احتجت إلى العودة إلى 1.x، فأعد نشر صورة 1.x على وحدة التخزين نفسها. أي شيء أنشأته في 2.0 بعد الترقية يقع في Postgres ولن يكون في قاعدة بيانات 1.x، لذا تراجع سريعاً إن كنت ستفعل.
