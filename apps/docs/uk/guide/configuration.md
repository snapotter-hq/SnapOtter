# Конфігурація {#configuration}

Уся конфігурація задається через змінні середовища. Кожна змінна має розумне значення за замовчуванням, тому SnapOtter працює одразу після встановлення, навіть якщо не задавати жодної з них.

## Змінні середовища {#environment-variables}

### Сервер {#server}

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `PORT` | `1349` | Порт, який прослуховує сервер. |
| `HOST` | `0.0.0.0` | IP-адреса, яку прослуховує сервер. У мережі типу bridge (за замовчуванням для `docker run` і Compose) залишайте `0.0.0.0` (або `::`), інакше опубліковані порти перестануть працювати. У нативному встановленні або в контейнері в мережі хоста `127.0.0.1` тримає API поза мережею; для віддаленого доступу поставте перед ним зворотний проксі. [Вбудований режим](#embedded-mode) працює лише з `0.0.0.0`, `::` або `127.0.0.1`, бо його перевірка запуску звертається до `127.0.0.1`. З будь-якою іншою адресою, зокрема `::1`, контейнер ніколи не вважається запущеним, а подальший збій зупиняє його замість перезапуску сервера. Будь-яке значення, що не є IP-адресою, зокрема `localhost`, зупиняє сервер під час запуску. |
| `BASE_PATH` | (порожньо) | Публічний шлях розгортання, наприклад `/snapotter`. Порожнє значення або `/` означає обслуговування з кореня домену. Застосовується під час роботи, перебудовувати образ не потрібно. |
| `RATE_LIMIT_PER_MIN` | `1000` | Максимальна кількість запитів на хвилину з одного IP. Значення 0 вимикає обмеження частоти запитів. |
| `API_KEYS_RATE_LIMIT_PER_MIN` | `30` | Максимальна кількість запитів на хвилину з одного IP до кінцевих точок керування API-ключами (перелік, створення, відкликання). Ключі, які використовуються для викликів інструментів, це не стосується. Задайте `0`, щоб зняти обмеження. |
| `CORS_ORIGIN` | (порожньо) | Дозволені джерела для CORS, розділені комами, або порожнє значення, щоб дозволити лише те саме джерело. |
| `LOG_LEVEL` | `info` | Докладність журналу. Одне зі значень: `fatal`, `error`, `warn`, `info`, `debug`, `trace`. |
| `TRUST_PROXY` | `loopback,linklocal,uniquelocal` | Які вузли можуть задавати IP клієнта через `X-Forwarded-For`. За замовчуванням довіра надається лише вузлу з приватної мережі, тому зворотний проксі в мережі Docker або в локальній мережі вважається довіреним, а підроблений заголовок від публічного клієнта ні. Задавайте `true` лише тоді, коли перед сервером стоїть підконтрольний вам проксі з публічною адресою. |
| `SNAPOTTER_ANALYTICS_DEFAULT` | `on` | Задайте `off`, щоб новий екземпляр стартував з вимкненою «Анонімною продуктовою аналітикою» і нічого не надсилав від першого запуску. Змінна лише заповнює це налаштування, поки ніхто не зробив вибору. Щойно налаштування збережено, адміністратором чи цією змінною, зміна змінної нічого не дає; адміністратор однаково може ввімкнути аналітику в розділі Налаштування > Система > Конфіденційність. |

### Автентифікація {#authentication}

Два булеві параметри нижче приймають лише `true` і `false`. Будь-яке інше значення, зокрема `1`, `yes` чи `on`, не проходить перевірку, і сервер завершує роботу ще до початку прослуховування.

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `AUTH_ENABLED` | `true` | Вимагати вхід. Значення `false` запускає систему взагалі без облікових записів, і тоді кожен запит отримує права адміністратора, тому використовуйте це лише в довіреній мережі. |
| `DEFAULT_USERNAME` | `admin` | Ім'я користувача початкового облікового запису адміністратора. Використовується лише під час першого запуску. |
| `DEFAULT_PASSWORD` | `admin` | Пароль початкового облікового запису адміністратора. Змініть його після першого входу. |
| `MAX_USERS` | `0` (без обмежень) | Максимальна кількість зареєстрованих облікових записів. Значення 0 означає без обмежень. |
| `SESSION_DURATION_HOURS` | `168` | Тривалість сеансу входу в годинах (за замовчуванням 7 днів). |
| `SKIP_MUST_CHANGE_PASSWORD` | `false` | Задайте `true`, щоб пропустити примусовий запит зміни пароля під час першого входу. |
| `LOGIN_ATTEMPT_LIMIT` | `30` | Максимальна кількість запитів на вхід за хвилину з одного IP. Подальші спроби отримують `429`, доки не мине хвилина. Повторні невдалі спроби для одного імені користувача зазвичай спочатку впираються в `LOGIN_THROTTLE_MAX_FAILURES`. Адміністратор може змінити це в Settings > System. Задайте `0`, щоб зняти обмеження. Збірка з вихідного коду починається з 10. |
| `LOGIN_THROTTLE_MAX_FAILURES` | `10` | Кількість невдалих входів за паролем, яку одне ім'я користувача може мати протягом `LOGIN_THROTTLE_WINDOW_S`, перш ніж подальші спроби для нього отримають `429`, з якого б IP вони не надходили. Спроби знову дозволяються, коли найстаріші невдачі виходять за межі вікна. Значення 0 вимикає обмеження. |
| `LOGIN_THROTTLE_WINDOW_S` | `900` | Тривалість цього вікна в секундах. Має бути щонайменше 1; сервер не запускається зі значенням 0. |

### Сховище {#storage}

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `STORAGE_MODE` | `local` | `local` або `s3`. Для S3 і MinIO потрібна ліцензія з функцією s3_storage, а також змінні `S3_*`, наведені нижче. |
| `DATABASE_URL` | `postgres://snapotter:snapotter@localhost:5432/snapotter` | Рядок підключення до PostgreSQL, через яке обробляється кожен запит. Починаючи з 2.3.0, задайте також `DATABASE_MIGRATION_URL`, і це підключення стане роллю виконання з мінімально необхідними привілеями: лише DML для таблиць застосунку і більше нічого. Стек Compose спрямовує його на свій сервіс `postgres`; залиште змінну незаданою (разом із `REDIS_URL`), щоб отримати вбудований режим. Щоб підключитися через unix-сокет, вкажіть каталог сокета в `host`, як у `postgres://user:pass@localhost/snapotter?host=/var/run/postgresql`, і змонтуйте цей каталог у контейнер. |
| `DATABASE_MIGRATION_URL` | (порожньо) | Привілейоване підключення, яке використовується лише під час запуску для виконання міграцій і видачі прав ролі виконання, а потім закривається до першого запиту. Якщо залишити порожнім, SnapOtter працює з однією роллю, і `DATABASE_URL` виконує обидві функції. Див. [Ролі з мінімальними привілеями](/uk/guide/database#least-privilege-roles). |
| `REDIS_URL` | `redis://localhost:6379` | Рядок підключення до Redis (використовується для черг завдань BullMQ). Compose спрямовує його на свій сервіс `redis`. Для unix-сокета використовуйте `unix:///run/redis/redis.sock?db=5` (додайте `&password=...`, якщо Redis його потребує) і змонтуйте сокет у контейнер. |
| `WORKSPACE_PATH` | `./tmp/workspace` | Каталог для тимчасових файлів під час обробки. Очищається автоматично. Образ задає `/tmp/workspace`. |
| `FILES_STORAGE_PATH` | `./data/files` | Каталог для постійних файлів користувачів (завантажені зображення, збережені результати). Образ задає `/data/files`. |
| `MAX_STORAGE_PER_USER_MB` | `5000` | Ліміт у мегабайтах на те, що кожен користувач зберігає в бібліотеці файлів. Збереження, яке його перевищить, відхиляється із зазначенням використаного обсягу та ліміту. Квота, задана для користувача, має пріоритет над цим значенням. Значення 0 означає без обмежень. |

### Об'єктне сховище S3 {#s3-object-storage}

Читається лише коли `STORAGE_MODE=s3`. Якщо пропустити будь-яку з трьох обов'язкових змінних, запуск завершиться помилкою з назвою пропущеної змінної.

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `S3_BUCKET` | (порожньо) | Бакет, у якому зберігаються завантаження та результати. Обов'язково. |
| `S3_ACCESS_KEY_ID` | (порожньо) | Ключ доступу. Обов'язково. У контейнері його можна змонтувати як файл через `S3_ACCESS_KEY_ID_FILE`. |
| `S3_SECRET_ACCESS_KEY` | (порожньо) | Секретний ключ. Обов'язково. Та сама угода про файли: `S3_SECRET_ACCESS_KEY_FILE`. |
| `S3_REGION` | `us-east-1` | Регіон бакета. |
| `S3_ENDPOINT` | (порожньо) | Власна кінцева точка для MinIO, R2, Backblaze та інших S3-сумісних сховищ. Порожнє значення означає AWS. |
| `S3_FORCE_PATH_STYLE` | `false` | Задайте `true` для MinIO і всього, що потребує `endpoint/bucket/key` замість адресації через віртуальний хост. |
| `S3_PREFIX` | (порожньо) | Префікс ключів, щоб в одному бакеті могло зберігатися кілька екземплярів. |

### Шифрування даних у спокої {#encryption-at-rest}

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `DATA_ENCRYPTION_KEY` | (порожньо) | 64 шістнадцяткові символи (32 байти). Шифрує чутливі налаштування, що зберігаються в базі даних. Усе, що не складається з 64 шістнадцяткових символів, відхиляється під час запуску. |
| `DATA_ENCRYPTION_KEY_PREVIOUS` | (порожньо) | Ключ, від якого ви переходите, у тому самому форматі. Задайте обидва під час ротації, щоб наявні рядки й надалі розшифровувалися, а потім приберіть цей. |

### Вбудований режим {#embedded-mode}

Запустіть образ без `DATABASE_URL` і без `REDIS_URL`, і він запустить власні PostgreSQL 17 та Redis усередині контейнера, прив'язані до loopback, з усіма даними на томі `/data`. Це повертає зручність запуску однією командою `docker run` для швидкого старту, домашньої лабораторії та оновлення з 1.x. Це шлях для зручності, а не промислове розгортання: для production запускайте стек Compose з трьох контейнерів з окремими PostgreSQL і Redis. Вбудований режим вимагає запуску контейнера від імені root і несумісний із середовищами, що працюють з довільним UID (OpenShift, Kubernetes `runAsNonRoot`); там використовуйте Compose.

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `EMBEDDED` | `auto` | Вмикається автоматично, коли `DATABASE_URL` і `REDIS_URL` обидві не задані. Задайте `0`, щоб вимкнути (тоді застосунок одразу завершиться з помилкою, якщо не задано зовнішній `DATABASE_URL`/`REDIS_URL`, замість того щоб непомітно запускати базу даних усередині контейнера). |
| `REDIS_MAXMEMORY` | `512mb` | Обмеження пам'яті для вбудованого Redis (лише у вбудованому режимі). Зменшуйте його на хостах з обмеженою пам'яттю, як-от Raspberry Pi. |
| `EMBEDDED_PG_PORT` | `5432` | Loopback-порт для вбудованого PostgreSQL (лише у вбудованому режимі). Змінюйте його лише тоді, коли контейнер спільно використовує мережу, де порт 5432 уже зайнятий, як-от з `--network host`. Він має відрізнятися від `EMBEDDED_REDIS_PORT` і бути більшим за 1023, бо PostgreSQL працює від імені непривілейованого користувача, який не може прив'язатися до привілейованого порту в мережі хоста. |
| `EMBEDDED_REDIS_PORT` | `6379` | Те саме для вбудованого Redis, який також працює від імені непривілейованого користувача. |
| `EMBEDDED_DB_PASSWORDS` | (порожньо) | Задайте `1`, щоб під час наступного запуску згенерувати випадкові паролі для ролей вбудованого PostgreSQL і для Redis; вони зберігаються в `/data/.embedded-db-secrets`. Після цього для входу через TCP потрібні ці паролі. На томі, вперше створеному версією 2.3.0 або новішою, суперкористувач PostgreSQL узагалі не може ввійти через TCP; на старішому томі власником бази даних є суперкористувач, і захищає його саме пароль. Використовуйте це щоразу, коли мережу контейнера спільно використовують інші програми, наприклад з `--network host`. Для цього тому параметр лишається ввімкненим: паролі використовуються під час кожного запуску, навіть якщо ви приберете цю змінну, а видалення `/data/.embedded-db-secrets` дає лише нові паролі або, якщо змінну не задано, запуск, що завершується помилкою. Якщо контейнер не запускається через пошкодження одного з цих файлів, видаліть цей файл командою `docker run --rm -v <volume>:/data --entrypoint rm snapotter/snapotter:<your tag> -r /data/.embedded-db-secrets/<name>` і знову запустіть контейнер; наступний запуск створить новий. Змінна приймає `1`, `0` або порожнє значення, а будь-яке інше значення зупиняє запуск. |
| `EMBEDDED_REDIS_TIMEOUT_S` | `180` | Кількість секунд, протягом яких запуск чекає, поки вбудований Redis відповість на `PING`, перш ніж здатися. Після тайм-ауту контейнер зупиняється і записує в журнал причину, а не зависає. Цілі секунди від 1 до 999999; значення «без обмежень» немає, бо нескінченне очікування є саме тим збоєм, який це обмеження має запобігти. Збільшуйте лише якщо повільний хост його перевищує. |
| `EMBEDDED_POSTGRES_TIMEOUT_S` | `600` | Те саме для вбудованого PostgreSQL. Відлік починається після завершення `initdb` під час першого запуску, тож він охоплює запуск сервера та відновлення після збою, а не початкове створення бази даних. |

Оновлення з 1.x: покладіть свій старий `snapotter.db` за шляхом `/data/snapotter.db` на томі, і вбудований режим імпортує його у вбудований PostgreSQL під час першого запуску. Імпорт виконується один раз, наступні запуски його пропускають.

Примітка щодо телеметрії: вбудований режим успадковує значення аналітики за замовчуванням з образу, як і будь-яка інша конфігурація. Опублікований образ постачається з увімкненою аналітикою; щоб вимкнути її, зберіть образ з `--build-arg SNAPOTTER_ANALYTICS=off`, задайте `SNAPOTTER_ANALYTICS_DEFAULT=off` до першого запуску або скористайтеся відмовою в адмін-панелі застосунку.

### Обмеження обробки {#processing-limits}

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `MAX_UPLOAD_SIZE_MB` | `0` (без обмежень) | Максимальний розмір файлу для одного завантаження в мегабайтах. Значення 0 означає без обмежень. Опублікований образ постачається з `0`; збірка з вихідного коду починається зі 100. |
| `MAX_BATCH_SIZE` | `0` (без обмежень) | Максимальна кількість файлів в одному пакетному запиті. Значення 0 означає без обмежень. Опублікований образ постачається з `0`; збірка з вихідного коду починається зі 100. |
| `CONCURRENT_JOBS` | `0` (авто) | Кількість пакетних завдань, що виконуються паралельно. Значення 0 автоматично визначає її за кількістю доступних ядер ЦП. |
| `MAX_MEGAPIXELS` | `0` (без обмежень у застосунку) | Максимально дозволена роздільна здатність зображення в мегапікселях. Значення 0 знімає власне обмеження SnapOtter. Декодер зображень усе одно відхиляє все, що перевищує приблизно 268 МП (16383 x 16383 пікселів), тож значення понад 268 нічого не змінює. |
| `MAX_CPU_UPSCALE_MP` | `4` | Найбільший вхідний файл у мегапікселях, який приймає AI-збільшення на хості без GPU. Збільшений результат також обмежується 16-кратним значенням цього параметра (64 MP за замовчуванням), тому високий коефіцієнт масштабування ще більше знижує ліміт на вхідні дані. Більше зображення зменшується до припустимого розміру перед збільшенням; якщо в результаті воно не стане більшим за оригінал, запит натомість відхиляється. Lanczos пропускає ліміт на вхідні дані, але не ліміт на результат. Значення 0 знімає обмеження, але потребує багато RAM: RealESRGAN завжди будує всередині 4x буфер. |
| `MAX_WORKSPACE_SIZE_GB` | `0` (без обмежень) | Ліміт у ГБ на сукупний розмір завантажень і збережених результатів у робочому просторі. Після його перевищення завантаження та запити до інструментів отримують 503, доки файли не застаріють після `FILE_MAX_AGE_HOURS`. Значення 0 означає без обмежень; локальне сховище все одно відхиляє записи з 503, коли на диску лишається менше 0,5 ГБ вільного місця. Опублікований образ постачається з `0`; збірка з вихідного коду починається з 10. |
| `MAX_WORKER_THREADS` | `0` (авто) | Максимальна кількість робочих потоків для обробки зображень. Значення 0 автоматично визначає її за кількістю доступних ядер ЦП. |
| `PROCESSING_TIMEOUT_S` | `0` (без обмежень) | Тайм-аут для кожного виклику Python sidecar, який виконує AI-інструменти, у секундах. Значення 0 вимикає тайм-аут. Він не обмежує завдання із зображеннями, PDF чи медіа; це роблять `JOB_TIMEOUT_FAST_S` і `JOB_TIMEOUT_LONG_S`. |

| `MAX_METADATA_TAG_LENGTH` | `10000` | Найдовше значення, яке «Редагування метаданих» записує в один тег (виконавець, опис, ключові слова тощо), у символах. ### Інструменти AI {#ai-tools}

Ці змінні читає Python sidecar. Задайте їх у середовищі контейнера (або в `.env` для опублікованих файлів Compose) і перезапустіть.

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `SNAPOTTER_GPU` | (порожньо) | Задайте `0`, `false` або `no`, щоб усі інструменти AI працювали на CPU, навіть якщо GPU є. Будь-яке інше значення або порожнє поле дає SnapOtter змогу використовувати виявлений GPU. Застосовуйте, якщо в невеликого GPU посеред завдання закінчується пам'ять або якщо через проблему з драйвером запуски на GPU завершуються помилкою. Частіше це актуально для нативних встановлень і LXC, які тепер використовують GPU, коли встановлено pip-пакет cuDNN. На CPU завдання виконуються повільніше, а для збільшення діє `MAX_CPU_UPSCALE_MP`. |
| `SD15_INPAINT_DIR` | `$MODELS_PATH/sd15-inpainting` | Тека з моделлю Stable Diffusion 1.5 для інпейнтингу (формат diffusers), яку «Видалення об'єктів» використовує у режимі високої якості. Сюди її кладе пакет функцій `inpaint-hq`, тому змінюйте шлях, лише якщо зберігаєте модель в іншому місці. `MODELS_PATH` SnapOtter задає як `ai/models` усередині каталогу даних. |
| `SD15_INPAINT_STEPS` | `28` | Кількість кроків шумозаглушення на одне видалення. Більше кроків може додати деталізації, а час зростає пропорційно. |
| `SD15_INPAINT_STRENGTH` | `0.95` | Наскільки сильно модель може перемалювати область під маскою, від 0 до 1. Менші значення зберігають більше вихідних пікселів (область спочатку заповнюється з оточення, потім злегка доопрацьовується). Більші значення дозволяють моделі перемальовувати вільніше, а `1` ігнорує оточення і малює з шуму, через що частіше з'являється вигаданий новий об'єкт. |
| `SD15_INPAINT_GUIDANCE` | `7.0` | Наскільки суворо модель дотримується підказок. Чим вище значення, тим буквальніше вона їх дотримується; дуже високі значення можуть давати різкий результат. |
| `SD15_INPAINT_PROMPT` | (порожньо) | Текст, що описує, що домалювати у видаленій області. Для видалення найкраще залишити порожнім, тоді модель продовжує оточення. |
| `SD15_INPAINT_NEGATIVE` | `object, person, text, watermark, artifact, blurry, distorted, extra limbs` | Текст, що описує, чого у видаленій області бути не повинно. Значення за замовчуванням не дає домальовувати на місці прогалини новий об'єкт. |
| `SD15_INPAINT_SEED` | `0` | Початкове значення генератора випадкових чисел. За фіксованого значення те саме зображення з тією самою маскою щоразу обробляється однаково. Змініть його, щоб отримати інший результат. |

### Рушії {#engines}

SnapOtter шукає кожен виконуваний файл обробки в `$PATH` усередині контейнера, тому ці змінні залишаються порожніми, якщо ви не монтуєте власну збірку.

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `FFMPEG_PATH` | (порожньо) | Шлях до виконуваного файлу `ffmpeg`, на якому працюють інструменти відео та аудіо. |
| `FFPROBE_PATH` | (порожньо) | Шлях до `ffprobe`, який читає медіафайли перед їх обробкою. Вкажіть ту саму збірку, що й для `FFMPEG_PATH`. |
| `QPDF_PATH` | (порожньо) | Шлях до `qpdf`, який використовують інструменти PDF і перевірка завантажених PDF. |
| `SOFFICE_PATH` | (порожньо) | Шлях до `soffice` з LibreOffice, який використовується для перетворення офісних документів. |
| `PDFCPU_PATH` | (порожньо) | Шлях до `pdfcpu`, який використовують деякі інструменти PDF. |
| `GS_PATH` | (порожньо) | Шлях до `gs` з Ghostscript, який використовують інструменти PDF і PDF OCR. |
| `PANDOC_PATH` | (порожньо) | Шлях до `pandoc`, який використовується для перетворення документів. |
| `SNAPOTTER_FONT_FILE` | (порожньо) | Файл шрифту для тексту, що накладається на відео (вбудовування субтитрів, водяний знак на відео). Порожнє значення означає перший шрифт, який знайде образ. |
| `SNAPOTTER_FONT_FAMILY` | (порожньо) | Назва сімейства шрифту з `SNAPOTTER_FONT_FILE`. Порожнє значення означає `Sans`. |
| `SNAPOTTER_HW_ACCEL` | (порожньо) | Сімейство апаратних відеокодувальників: `nvenc` або `vaapi`. Порожнє значення кодує програмно. |

`SNAPOTTER_HW_ACCEL` потребує ffmpeg, зібраного з підтримкою цього сімейства кодувальників, а в ffmpeg з образу немає жодного з них. З власним виконуваним файлом образу налаштування повертається до програмного кодування і повідомляє про це в журналі запуску. Щоб скористатися ним, змонтуйте власну збірку ffmpeg, вкажіть на неї `FFMPEG_PATH` і `FFPROBE_PATH` та надайте контейнеру пристрій GPU. Для `nvenc` також задайте `NVIDIA_DRIVER_CAPABILITIES=compute,utility,video`: образ запитує лише `compute,utility`, а без `video` середовище виконання NVIDIA не монтує бібліотеку кодування, тож кодувальник присутній у списку, але кожне кодування завершується помилкою. Перевизначення шляху, що не існує або не є виконуваним, також зазначається в журналі запуску, і кожне завдання, якому потрібен цей файл, завершуватиметься помилкою, доки ви не виправите шлях або не приберете його.

Опубліковані файли Compose передають усі ці змінні з `.env`, тому достатньо задати їх там.

Адміністратор може змінити це в Settings > System. Користувачі та команди під юридичним утриманням зберігають свої записи. Значення 0 зберігає їх назавжди. |

| `SNAPOTTER_LICENSE_KEY` | (порожньо) | Ліцензійний ключ, що відкриває корпоративні функції, як-от SAML, SCIM і сховище S3. Читається під час запуску, тому після зміни перезапустіть. Недійсний або прострочений ключ записує попередження в журнал, а сервер працює без цих функцій. У контейнері його можна натомість підключити через `SNAPOTTER_LICENSE_KEY_FILE` (див. [Docker secrets](/uk/guide/security#docker-secrets)). |

## Приклад для Docker {#docker-example}

```yaml
services:
  SnapOtter:
    image: snapotter/snapotter:latest
    ports:
      - "1349:1349"
    volumes:
      - SnapOtter-data:/data
      - SnapOtter-workspace:/tmp/workspace
    environment:
      - AUTH_ENABLED=true
      - DEFAULT_USERNAME=admin
      - DEFAULT_PASSWORD=changeme
      - DATABASE_URL=postgres://snapotter:snapotter@postgres:5432/snapotter
      - REDIS_URL=redis://redis:6379
      - MAX_UPLOAD_SIZE_MB=200
      - CONCURRENT_JOBS=4
      - FILE_MAX_AGE_HOURS=12
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped

  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: snapotter
      POSTGRES_PASSWORD: snapotter     # Change this for non-local deployments
      POSTGRES_DB: snapotter
    volumes:
      - SnapOtter-pgdata:/var/lib/postgresql/data
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U snapotter -d snapotter"]
      interval: 10s
      timeout: 5s
      retries: 12

  redis:
    image: redis:8-alpine
    command: ["redis-server", "--maxmemory-policy", "noeviction", "--appendonly", "yes"]
    volumes:
      - SnapOtter-redisdata:/data
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 12

volumes:
  SnapOtter-data:
  SnapOtter-workspace:
  SnapOtter-pgdata:
  SnapOtter-redisdata:
```

## Томи {#volumes}

Стек Docker Compose використовує чотири томи:

- `/data` (app) - моделі ШІ, віртуальне середовище Python та файли користувачів. Змонтуйте його, щоб зберігати завантажені файли та встановлені пакети ШІ між перезапусками.
- `/tmp/workspace` (app) - тимчасове сховище для файлів, що обробляються. Може бути ефемерним, але монтування запобігає заповненню доступного для запису шару контейнера.
- `SnapOtter-pgdata` (postgres) - каталог даних PostgreSQL. Тут зберігаються всі реляційні дані (користувачі, налаштування, конвеєри, завдання, журнал аудиту). Резервне копіювання через `pg_dump` або знімок тому.
- `SnapOtter-redisdata` (redis) - файл Redis лише для додавання для довговічних черг завдань.
