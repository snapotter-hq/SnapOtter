# База даних {#database}

SnapOtter використовує PostgreSQL 17 з [Drizzle ORM](https://orm.drizzle.team/) (pg-core / node-postgres) для збереження даних. Схема визначена в `apps/api/src/db/schema.ts`.

Підключення налаштовується через змінну середовища `DATABASE_URL` (за замовчуванням `postgres://snapotter:snapotter@postgres:5432/snapotter`). У Docker Compose контейнер Postgres зберігає свої дані в іменованому томі `SnapOtter-pgdata`. Запити обслуговуються від імені ролі, яка може лише читати й записувати рядки; про це йдеться нижче в розділі [Ролі з мінімальними привілеями](#least-privilege-roles).

## Таблиці {#tables}

### users {#users}

Зберігає облікові записи користувачів. Створюється автоматично під час першого запуску з `DEFAULT_USERNAME` та `DEFAULT_PASSWORD`.

| Стовпець | Тип | Примітки |
|---|---|---|
| `id` | uuid | Первинний ключ |
| `username` | varchar | Унікальне, обов'язкове |
| `passwordHash` | varchar | Хеш scrypt |
| `role` | varchar | `admin`, `editor` або `user` |
| `mustChangePassword` | boolean | Позначка примусового скидання пароля |
| `createdAt` | timestamp | Час створення |
| `updatedAt` | timestamp | Час останнього оновлення |

### sessions {#sessions}

Активні сеанси входу. Кожен рядок пов'язує токен сеансу з користувачем.

| Стовпець | Тип | Примітки |
|---|---|---|
| `id` | varchar | Первинний ключ (токен сеансу) |
| `userId` | uuid | Зовнішній ключ на `users.id` |
| `expiresAt` | timestamp | Час завершення дії |
| `createdAt` | timestamp | Час створення |

### teams {#teams}

Групи для організації користувачів. Адміністратори можуть призначати користувачів до команд.

| Стовпець | Тип | Опис |
|--------|------|-------------|
| `id` | uuid | Первинний ключ |
| `name` | varchar (унікальне, до 50 символів) | Назва команди |
| `createdAt` | timestamp | Час створення |

### api_keys {#api-keys}

Ключі API для програмного доступу. Необроблений ключ показується один раз під час створення; зберігається лише хеш.

| Стовпець | Тип | Примітки |
|---|---|---|
| `id` | uuid | Первинний ключ |
| `userId` | uuid | Зовнішній ключ на `users.id` |
| `keyHash` | varchar | Хеш scrypt ключа |
| `name` | varchar | Мітка, задана користувачем |
| `createdAt` | timestamp | Час створення |
| `lastUsedAt` | timestamp | Оновлюється при кожному автентифікованому запиті |

Ключі мають префікс `si_`, після якого йдуть 96 шістнадцяткових символів (48 випадкових байтів).

### pipelines {#pipelines}

Збережені ланцюжки інструментів, які користувачі створюють в інтерфейсі.

| Стовпець | Тип | Примітки |
|---|---|---|
| `id` | uuid | Первинний ключ |
| `name` | varchar | Назва конвеєра |
| `description` | varchar | Необов'язковий опис |
| `steps` | jsonb | Масив об'єктів `{ toolId, settings }` |
| `createdAt` | timestamp | Час створення |

### user_files {#user-files}

Постійна бібліотека файлів. Збережена правка за замовчуванням вставляється як незалежний кореневий рядок («зберегти як нову»: `version` 1, `parentId` null, тож оригінал залишається в списку) або як версія, пов'язана з батьківською, якщо ви перезаписуєте оригінал (`parentId` задано, `version` збільшено, оригінал замінюється). Стовпець `toolChain` фіксує застосовані інструменти.

| Стовпець | Тип | Опис |
|--------|------|-------------|
| `id` | uuid | Первинний ключ |
| `userId` | uuid | Зовнішній ключ на users (CASCADE DELETE) |
| `originalName` | varchar | Початкова назва завантаженого файлу |
| `storedName` | varchar | Назва файлу на диску |
| `mimeType` | varchar | Тип MIME |
| `size` | integer | Розмір файлу в байтах |
| `width` | integer | Ширина зображення в пікселях |
| `height` | integer | Висота зображення в пікселях |
| `version` | integer | Номер версії (1 = оригінал) |
| `parentId` | uuid або null | Зовнішній ключ на user_files (батьківська версія) |
| `toolChain` | jsonb | Ідентифікатори інструментів, застосованих по черзі для отримання цієї версії |
| `createdAt` | timestamp | Час створення |

### jobs {#jobs}

Відстежує завдання обробки для відображення прогресу та очищення.

| Стовпець | Тип | Примітки |
|---|---|---|
| `id` | uuid | Первинний ключ |
| `type` | varchar | Ідентифікатор інструмента або конвеєра |
| `status` | varchar | `queued`, `processing`, `completed` або `failed` |
| `progress` | real | Частка від 0.0 до 1.0 |
| `inputFiles` | jsonb | Масив шляхів до вхідних файлів |
| `outputPath` | varchar | Шлях до файлу результату |
| `settings` | jsonb | Використані налаштування інструмента |
| `error` | varchar | Повідомлення про помилку в разі збою |
| `createdAt` | timestamp | Час створення |
| `completedAt` | timestamp | Час завершення |

### settings {#settings}

Сховище «ключ-значення» для налаштувань усього сервера, які адміністратори можуть змінювати в інтерфейсі.

| Стовпець | Тип | Примітки |
|---|---|---|
| `key` | varchar | Первинний ключ |
| `value` | varchar | Значення налаштування |
| `updatedAt` | timestamp | Час останнього оновлення |

### roles {#roles}

Власні ролі з докладними дозволами.

| Стовпець | Тип | Примітки |
|---|---|---|
| `id` | uuid | Первинний ключ |
| `name` | varchar | Унікальна назва ролі |
| `description` | varchar | Необов'язковий опис |
| `permissions` | jsonb | Масив рядків дозволів |
| `createdAt` | timestamp | Час створення |

### audit_log {#audit-log}

Журнал дій, важливих для безпеки.

| Стовпець | Тип | Примітки |
|---|---|---|
| `id` | uuid | Первинний ключ |
| `userId` | uuid | Зовнішній ключ на users |
| `action` | varchar | Тип дії |
| `details` | jsonb | Дані, специфічні для дії |
| `createdAt` | timestamp | Час дії |

### user_preferences {#user-preferences}

Стан інтерфейсу для кожного користувача, з ключем за назвою параметра. Через `PUT /api/v1/preferences` забезпечує закріплені інструменти на панелі.

| Стовпець | Тип | Примітки |
|---|---|---|
| `userId` | text | Зовнішній ключ на users, видаляється каскадно. Первинний ключ разом з `key` |
| `key` | text | Назва параметра. Первинний ключ разом з `userId` |
| `value` | jsonb | Дані параметра |
| `updatedAt` | timestamp | Час останнього запису |

## Міграції {#migrations}

Міграціями схеми керує Drizzle. Файли міграцій розташовані в `apps/api/drizzle/`. Під час розробки:

```bash
cd apps/api
npx drizzle-kit generate   # generate a migration from schema changes
npx drizzle-kit migrate    # apply pending migrations
```

У production відкладені міграції застосовуються автоматично під час запуску.

## Ролі з мінімальними привілеями {#least-privilege-roles}

Дві ролі, дві задачі. `DATABASE_URL` обслуговує запити і має `SELECT`, `INSERT`, `UPDATE`, `DELETE` для таблиць застосунку, а також `USAGE` і `SELECT` для їхніх послідовностей. Це весь перелік. Ця роль не може створювати чи видаляти таблиці, встановлювати розширення, виконувати `TRUNCATE`, читати `pg_authid`, створювати базу даних, змінювати роль або чіпати схему `drizzle`, де зберігається історія міграцій.

`DATABASE_MIGRATION_URL` є привілейованою. Вона виконує міграції та видає права ролі виконання під час запуску, а потім закривається до того, як буде обслуговано хоч один запит.

Цей поділ постачається в SnapOtter 2.3.0. Починаючи з цього випуску, файли Compose з репозиторію та образ «все в одному» налаштовані саме так, зокрема й наявні встановлення: під час запуску SnapOtter створює роль виконання, якщо її немає, видає їй права, виконує міграції, а потім поширює права на таблиці, які існували раніше. Для оновлення жодного ручного SQL не потрібно.

Образ 2.2.0 читає лише рядок підключення ролі виконання і ніколи не створює другу роль, тому якщо передати йому поділ, він не запуститься: журнал застосунку показує збій автентифікації за паролем для цієї ролі, а журнал Postgres повідомляє, що ролі не існує. Оновіть образ до 2.3.0 або новішого, перш ніж переходити у файлі Compose на поділ.

Якщо залишити `DATABASE_MIGRATION_URL` порожнім, система працює з однією роллю, і `DATABASE_URL` виконує обидві функції точно так само, як і до поділу. Це підтримувана конфігурація, а не застаріла. Вона є правильним вибором для керованого Postgres, де створення ролей часто не залежить від вас.

### Зовнішній і керований Postgres {#external-and-managed-postgres}

На RDS, Supabase, Cloud SQL або в будь-якому кластері, яким ви керуєте самостійно, поділ вмикається за бажанням. Створіть роль виконання один раз:

```sql
CREATE ROLE snapotter_app LOGIN PASSWORD 'choose-a-strong-password'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS;
```

Потім передайте SnapOtter обидва рядки підключення, що вказують на той самий хост, порт і базу даних:

```bash
DATABASE_URL=postgres://snapotter_app:choose-a-strong-password@db.example.com:5432/snapotter
DATABASE_MIGRATION_URL=postgres://snapotter:the-owner-password@db.example.com:5432/snapotter
```

На цьому зупиніться. SnapOtter сам застосовує права й повторно застосовує їх після кожної міграції, тому таблиця, додана в майбутньому випуску, буде охоплена без жодного SQL від вас.

Роль у `DATABASE_MIGRATION_URL` має бути власником таблиць SnapOtter, адже лише власник таблиці може видавати на неї права. У наявному встановленні це означає роль, від імені якої ви досі запускали SnapOtter, а не нову, створену для цієї мети. Якщо вказати нову роль, яка нічим не володіє, запуск завершиться помилкою, що говорить саме про це. Їй також потрібен `CREATEROLE`, щоб створювати й підтримувати роль виконання, а також право створювати схему `drizzle`.

Якщо в обох URL вказати ту саму роль, поділ вимикається, і SnapOtter повідомляє про це в журналі, а не вдає, що це не так. Якщо ваш провайдер не надає ролі, яка може одночасно володіти таблицями та мати `CREATEROLE`, працюйте з однією роллю.

### Чому біт суперкористувача не чіпають {#why-the-superuser-bit-is-left-alone}

SnapOtter ніколи сам не забирає `SUPERUSER` у ролі. У встановленні, створеному до поділу, `snapotter` є єдиним суперкористувачем кластера, і його пониження залишило б кластер без жодного, а відновити його можна лише через однокористувацький режим із зупиненим сервером. Захист забезпечується натомість переведенням довготривалого підключення на обмежену роль. Суперкористувач присутній у з'єднанні лише на кілька секунд запуску, а потім зникає.

У нових встановленнях «все в одному» такої проблеми немає. Вони отримують три ролі: `postgres` (початковий суперкористувач, якого немає в жодному рядку підключення, що використовує SnapOtter), `snapotter` (`NOSUPERUSER`, володіє даними, підключається лише під час запуску) та `snapotter_app` (лише рядки, обслуговує запити).

Щоб усе ж понизити старіший `snapotter`, спершу створіть другого суперкористувача й увійдіть під ним, щоб переконатися, що він працює. Потім `ALTER ROLE snapotter NOSUPERUSER`.

## Резервне копіювання та відновлення {#backup-and-restore}

Реляційна база даних зберігається на томі `SnapOtter-pgdata` контейнера Postgres, а не на томі `/data` застосунку.

**Логічне резервне копіювання з перевіркою (рекомендовано)**

```bash
# Dump into PostgreSQL's portable custom archive format
docker exec SnapOtter-postgres \
  pg_dump --format=custom --no-owner -U snapotter snapotter > snapotter.dump
test -s snapotter.dump
docker exec -i SnapOtter-postgres pg_restore --list < snapotter.dump >/dev/null

# Restore into a fresh/disposable target first and fail on the first SQL error
docker exec -i SnapOtter-postgres \
  pg_restore --exit-on-error --clean --if-exists --no-owner \
  -U snapotter -d snapotter < snapotter.dump
```

Обидві команди підключаються як `snapotter`, власник, і так мають робити й надалі. Роль виконання не бачить схеми `drizzle`, тому дамп, зроблений від її імені, вийшов би неповним. `--no-owner` залишає відновлені об'єкти у власності того, хто виконує відновлення, тому запуск від імені власника ставить власність туди, де на неї очікують права. Одне застереження для нового кластера: `pg_dump` містить права, але не ролі, на які вони посилаються, тому створіть `snapotter_app` перед відновленням, інакше `--exit-on-error` зупиниться на першому `GRANT`. SnapOtter у будь-якому разі повторно застосує права під час наступного запуску.

Цей дамп бази даних не містить збережених об'єктів бібліотеки в `/data/files` чи довговічного стану BullMQ у Redis. Резервне копіювання й відновлення їх виконуйте за узгодженою процедурою з розділу [Безпека та посилення захисту](/uk/guide/security#backup-and-recovery).

**Холодний знімок тому**

```bash
# Stop every service first, then use your storage platform to snapshot the
# PostgreSQL, app-data, and Redis volumes as one crash-consistent set.
docker compose -f docker/docker-compose.yml stop
```

Не копіюйте робочий каталог даних PostgreSQL за допомогою `tar`. Compose додає до назв томів префікс проєкту, тож визначайте ідентифікатори змонтованих томів через `docker inspect` або вашу платформу зберігання, а не припускайте буквальну мітку `SnapOtter-pgdata`.

### Міграція з 1.x (SQLite) {#migrating-from-1-x-sqlite}

Оновлення з SnapOtter 1.x має власний посібник: див. [Оновлення з 1.x до 2.0](./upgrading). Коротко: використайте наявний том `/data`, і 2.0 автоматично знайде та імпортує `/data/snapotter.db` під час першого запуску (або задайте `SQLITE_MIGRATE_PATH`, щоб вказати на нього явно). Спершу зробіть резервну копію всього тому `/data`, а не лише `snapotter.db`: 1.x використовує режим WAL у SQLite, тож зупинений контейнер часто залишає більшість даних у `snapotter.db-wal` поруч із майже порожнім `snapotter.db`.
