# Оновлення з 1.x до 2.0 {#upgrading-from-1-x-to-2-0}

SnapOtter 1.x зберігав усе в одному файлі SQLite і працював як один контейнер. SnapOtter 2.0 використовує PostgreSQL і Redis. Цей посібник описує перенесення встановлення 1.x на 2.0 без втрати даних.

Коротко: використайте наявний том `/data`, і 2.0 автоматично імпортує вашу базу даних 1.x під час першого запуску. Ваші користувачі, збережені файли, налаштування, ключі API та конвеєри переносяться. Стара база даних ніколи не змінюється, тому ви завжди можете відкотитися.

::: tip Примітка для наших користувачів 1.x
Багато з вас довіряють SnapOtter від першого дня, і ваші відгуки сформували цей реліз. У 2.0 під капотом багато змінилося, і цей посібник існує, щоб перехід не коштував вам нічого важливого. Ваші облікові записи, файли, налаштування, ключі API та конвеєри переносяться, а стара база даних залишається недоторканою. Дякуємо, що оновлюєтеся разом з нами.
:::

## Перш ніж почати: зробіть резервну копію всього тому `/data` {#before-you-start-back-up-the-whole-data-volume}

Робіть це спершу, щоразу. Копіюйте **весь** том `/data`, а не лише файл `snapotter.db`.

Ось чому це важливо. 1.x використовує SQLite у режимі WAL, тому зупинений контейнер 1.x зазвичай залишає більшість зафіксованих даних у `snapotter.db-wal` поруч із майже порожнім `snapotter.db`. Копіювання лише `snapotter.db` захоплює порожню базу даних і мовчки втрачає все. Том містить `snapotter.db`, `snapotter.db-wal`, `snapotter.db-shm` і ваш каталог `files/` разом, і вони мають переноситися як єдиний набір.

```bash
# Adjust the volume name to match yours (see "Check your volume name" below).
docker run --rm -v SnapOtter-data:/data -v "$PWD":/backup \
  alpine tar czf /backup/snapotter-1x-data.tgz -C /data .
```

## Спершу оновіться до 1.17.2 {#upgrade-to-1-17-2-first}

Перед переходом на 2.0 оновіть встановлення 1.x до найновішого релізу 1.x (1.17.2). Це дозволяє 1.x виконати власні фінальні міграції схеми, тож 2.0 імпортує з відомої, повної схеми. Оновлення зі старішої 1.x одразу на 2.0 не підтримується.

## Перевірте назву тому {#check-your-volume-name}

Імпортер бачить ваші дані лише тоді, коли стек 2.0 монтує той самий том, який використовувало встановлення 1.x. Назви томів Docker чутливі до регістру, а старіші фрагменти README використовували `snapotter-data` у нижньому регістрі, тоді як файли Compose використовують `SnapOtter-data`. Підтвердіть, який варіант у вас:

```bash
docker volume ls | grep -i snapotter
```

Використовуйте саме цю назву у своїй конфігурації 2.0.

## Шлях A: єдиний контейнер (найшвидший) {#path-a-single-container-quickest}

Якщо ви запускаєте SnapOtter через один `docker run`, продовжуйте так само. 2.0 стартує вбудовані PostgreSQL і Redis усередині контейнера, коли ви не задаєте `DATABASE_URL` або `REDIS_URL`, і автоматично виявляє та імпортує `/data/snapotter.db` під час першого запуску.

```bash
docker run -d --name snapotter -p 1349:1349 \
  -v SnapOtter-data:/data \
  snapotter/snapotter:latest
```

Стежте в журналах за рядком на кшталт:

```
Imported 1.x SQLite database: {"tables":{"users":2,"teams":1,...},"blobs":{"present":1,"missing":0}}
```

Це все. Увійдіть зі своїми наявними обліковими даними.

## Шлях B: Compose (рекомендовано для production) {#path-b-compose-recommended-for-production}

Стек Compose 2.0 запускає три сервіси (застосунок, Postgres, Redis). Використайте свій том `/data` з 1.x для сервісу застосунку. Застосунок автоматично виявляє `/data/snapotter.db` і імпортує його в Postgres під час першого запуску.

```yaml
services:
  SnapOtter:
    image: snapotter/snapotter:latest
    volumes:
      - SnapOtter-data:/data          # your existing 1.x volume
      - SnapOtter-workspace:/tmp/workspace
    environment:
      - DATABASE_URL=postgres://${POSTGRES_APP_USER:-snapotter_app}:${POSTGRES_APP_PASSWORD:-snapotter_app}@postgres:5432/${POSTGRES_DB:-snapotter}
      - DATABASE_MIGRATION_URL=postgres://${POSTGRES_USER:-snapotter}:${POSTGRES_PASSWORD:-snapotter}@postgres:5432/${POSTGRES_DB:-snapotter}
      - REDIS_URL=redis://:snapotter@redis:6379
    # ...
```

Якщо ви волієте явно вказати на стару базу даних, задайте `SQLITE_MIGRATE_PATH=/data/snapotter.db`. Явний шлях завжди має перевагу над автовиявленням.

## Попередній перегляд імпорту (необов'язково) {#preview-the-import-first-optional}

Щоб побачити, що саме буде імпортовано, нічого не записуючи, виконайте пробний запуск для вашого файла бази даних:

```bash
pnpm --filter @snapotter/api migrate:sqlite -- /path/to/snapotter.db --dry-run
```

Він виводить кількість рядків у кожній таблиці, скільки файлів збереженої бібліотеки знайдено на диску та які статуси завдань буде нормалізовано. Запущений Postgres не потрібен.

## Що переноситься, а що ні {#what-carries-over-and-what-does-not}

Переноситься:

- Користувачі та можливість входу. Хеші паролів не змінюються, тож те саме ім'я користувача й пароль працюють.
- Команди, налаштування (зокрема ідентичність вашого екземпляра), ролі, ключі API (вони продовжують працювати) та збережені конвеєри.
- Записи історії завдань.
- Ваша збережена бібліотека файлів, і записи, і самі файли, оскільки `/data/files` зберігається на томі.

Не переноситься:

- Сесії входу. Усі входять один раз після оновлення. Облікові дані не змінюються, тож це один повторний вхід, не більше.
- Вхідні та вихідні файли старих завдань обробки. Вони зберігалися в тимчасовому робочому просторі й навмисно зникли. Записи історії завдань залишаються.
- Позначки згоди на аналітику для кожного користувача з 1.x, які не мають еквівалента в 2.0 (аналітика 2.0 є налаштуванням рівня екземпляра).

## Вимкнення імпорту {#turning-the-import-off}

Якщо ви свідомо хочете нову базу даних, навіть коли на томі присутній `snapotter.db`, задайте `SQLITE_MIGRATE_PATH=off`.

## Якщо в екземплярі 2.0 уже є дані {#if-you-already-have-data-in-the-2-0-instance}

Імпортер працює лише з порожньою базою даних. Якщо ви запустили 2.0 з нуля (створивши дані), а потім змонтували старий `snapotter.db`, 2.0 виявить його, але не імпортуватиме, адже злиття двох наборів даних може спричинити конфлікти ID. У журналах з'явиться попередження. Щоб імпортувати дані 1.x, потрібен порожній екземпляр:

- Якщо екземпляр 2.0 містить лише типового адміністратора (ви ним фактично не користувалися), зупиніть стек, видаліть том Postgres (`SnapOtter-pgdata`) і запустіть знову зі старим `/data`. Імпорт пройде чисто. Це стирає лише тимчасові дані Postgres, а не вашу базу даних 1.x.
- Якщо екземпляр 2.0 містить справжні дані, які ви хочете зберегти, два набори даних не можна об'єднати автоматично. Експортуйте потрібне й імпортуйте дані 1.x в окреме нове розгортання.

## Відкат {#rolling-back}

Оновлення ніколи не змінює і не видаляє ваш `snapotter.db` з 1.x. Якщо потрібно повернутися до 1.x, розгорніть образ 1.x на тому самому томі. Усе, що ви створили в 2.0 після оновлення, зберігається в Postgres і не буде в базі даних 1.x, тому відкочуйтеся швидко, якщо збираєтеся це зробити.
