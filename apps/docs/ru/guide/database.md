# База данных {#database}

SnapOtter использует PostgreSQL 17 с [Drizzle ORM](https://orm.drizzle.team/) (pg-core / node-postgres) для хранения данных. Схема определена в `apps/api/src/db/schema.ts`.

Подключение настраивается переменной окружения `DATABASE_URL` (по умолчанию `postgres://snapotter:snapotter@postgres:5432/snapotter`). В Docker Compose контейнер Postgres хранит данные в именованном томе `SnapOtter-pgdata`. Запросы обслуживаются под ролью, которая может только читать и записывать строки, о чем рассказывается ниже в разделе [Роли с минимальными привилегиями](#least-privilege-roles).

## Таблицы {#tables}

### users {#users}

Хранит учетные записи пользователей. Создается автоматически при первом запуске из `DEFAULT_USERNAME` и `DEFAULT_PASSWORD`.

| Столбец | Тип | Примечания |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `username` | varchar | Уникальное, обязательное |
| `passwordHash` | varchar | Хеш scrypt |
| `role` | varchar | `admin`, `editor` или `user` |
| `mustChangePassword` | boolean | Флаг принудительного сброса пароля |
| `createdAt` | timestamp | Время создания |
| `updatedAt` | timestamp | Время последнего обновления |

### sessions {#sessions}

Активные сессии входа. Каждая строка связывает токен сессии с пользователем.

| Столбец | Тип | Примечания |
|---|---|---|
| `id` | varchar | Первичный ключ (токен сессии) |
| `userId` | uuid | Внешний ключ на `users.id` |
| `expiresAt` | timestamp | Время истечения |
| `createdAt` | timestamp | Время создания |

### teams {#teams}

Группы для организации пользователей. Администраторы могут назначать пользователей в команды.

| Столбец | Тип | Описание |
|--------|------|-------------|
| `id` | uuid | Первичный ключ |
| `name` | varchar (уникальное, не более 50 символов) | Название команды |
| `createdAt` | timestamp | Время создания |

### api_keys {#api-keys}

API-ключи для программного доступа. Исходный ключ показывается один раз при создании; хранится только хеш.

| Столбец | Тип | Примечания |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `userId` | uuid | Внешний ключ на `users.id` |
| `keyHash` | varchar | Хеш scrypt ключа |
| `name` | varchar | Метка, заданная пользователем |
| `createdAt` | timestamp | Время создания |
| `lastUsedAt` | timestamp | Обновляется при каждом аутентифицированном запросе |

Ключи имеют префикс `si_`, за которым следуют 96 шестнадцатеричных символов (48 случайных байт).

### pipelines {#pipelines}

Сохраненные цепочки инструментов, которые пользователи создают в интерфейсе.

| Столбец | Тип | Примечания |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `name` | varchar | Название конвейера |
| `description` | varchar | Необязательное описание |
| `steps` | jsonb | Массив объектов `{ toolId, settings }` |
| `createdAt` | timestamp | Время создания |

### user_files {#user-files}

Постоянная библиотека файлов. Сохраненная правка по умолчанию вставляется как независимая корневая строка («сохранить как новый»: `version` равно 1, `parentId` равно null, так что оригинал остается в списке), либо как версия со ссылкой на родителя, когда вы перезаписываете оригинал (`parentId` задан, `version` увеличен, он заменяет оригинал). Столбец `toolChain` фиксирует примененные инструменты.

| Столбец | Тип | Описание |
|--------|------|-------------|
| `id` | uuid | Первичный ключ |
| `userId` | uuid | Внешний ключ на users (CASCADE DELETE) |
| `originalName` | varchar | Исходное имя загруженного файла |
| `storedName` | varchar | Имя файла на диске |
| `mimeType` | varchar | Тип MIME |
| `size` | integer | Размер файла в байтах |
| `width` | integer | Ширина изображения в px |
| `height` | integer | Высота изображения в px |
| `version` | integer | Номер версии (1 = оригинал) |
| `parentId` | uuid или null | Внешний ключ на user_files (родительская версия) |
| `toolChain` | jsonb | Идентификаторы инструментов, примененных по порядку для получения этой версии |
| `createdAt` | timestamp | Время создания |

### jobs {#jobs}

Отслеживает задачи обработки для отображения прогресса и очистки.

| Столбец | Тип | Примечания |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `type` | varchar | Идентификатор инструмента или конвейера |
| `status` | varchar | `queued`, `processing`, `completed` или `failed` |
| `progress` | real | Доля от 0.0 до 1.0 |
| `inputFiles` | jsonb | Массив путей входных файлов |
| `outputPath` | varchar | Путь к файлу результата |
| `settings` | jsonb | Использованные настройки инструмента |
| `error` | varchar | Сообщение об ошибке при сбое |
| `createdAt` | timestamp | Время создания |
| `completedAt` | timestamp | Время завершения |

### settings {#settings}

Хранилище «ключ-значение» для настроек всего сервера, которые администраторы могут менять из интерфейса.

| Столбец | Тип | Примечания |
|---|---|---|
| `key` | varchar | Первичный ключ |
| `value` | varchar | Значение настройки |
| `updatedAt` | timestamp | Время последнего обновления |

### roles {#roles}

Пользовательские роли с детальными правами.

| Столбец | Тип | Примечания |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `name` | varchar | Уникальное название роли |
| `description` | varchar | Необязательное описание |
| `permissions` | jsonb | Массив строк прав |
| `createdAt` | timestamp | Время создания |

### audit_log {#audit-log}

Журнал действий, важных для безопасности.

| Столбец | Тип | Примечания |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `userId` | uuid | Внешний ключ на users |
| `action` | varchar | Тип действия |
| `details` | jsonb | Данные, специфичные для действия |
| `createdAt` | timestamp | Время действия |

### user_preferences {#user-preferences}

Состояние интерфейса для каждого пользователя, по имени настройки. Обеспечивает закрепленные инструменты панели через `PUT /api/v1/preferences`.

| Столбец | Тип | Примечания |
|---|---|---|
| `userId` | text | Внешний ключ на users, каскадное удаление. Первичный ключ вместе с `key` |
| `key` | text | Название настройки. Первичный ключ вместе с `userId` |
| `value` | jsonb | Содержимое настройки |
| `updatedAt` | timestamp | Последняя запись |

## Миграции {#migrations}

Миграциями схемы занимается Drizzle. Файлы миграций находятся в `apps/api/drizzle/`. Во время разработки:

```bash
cd apps/api
npx drizzle-kit generate   # generate a migration from schema changes
npx drizzle-kit migrate    # apply pending migrations
```

В продакшене ожидающие миграции применяются автоматически при запуске.

## Роли с минимальными привилегиями {#least-privilege-roles}

Две роли, две задачи. `DATABASE_URL` обслуживает запросы и имеет `SELECT`, `INSERT`, `UPDATE`, `DELETE` на таблицах приложения, а также `USAGE` и `SELECT` на их последовательностях. Это весь список. Она не может создавать или удалять таблицы, устанавливать расширения, `TRUNCATE`, читать `pg_authid`, создавать базу данных, изменять роль или трогать схему `drizzle`, где хранится история миграций.

`DATABASE_MIGRATION_URL` является привилегированной. Она выполняет миграции и выдает права роли времени выполнения при загрузке, затем закрывается до обслуживания первого запроса.

Это разделение поставляется в SnapOtter 2.3.0. Начиная с этого релиза файлы Compose в репозитории и образ «все в одном» настроены именно так, включая существующие установки: при загрузке SnapOtter создает роль времени выполнения, если ее нет, выдает ей права, выполняет миграции, затем распространяет права на таблицы, существовавшие ранее. Для обновления не нужен ручной SQL.

Образ 2.2.0 читает только строку подключения времени выполнения и никогда не создает вторую роль, поэтому если передать ему разделение, он не запустится: журнал приложения показывает ошибку парольной аутентификации для этой роли, а журнал Postgres сообщает, что роли не существует. Обновите образ до 2.3.0 или новее, прежде чем переключать файл Compose на разделение.

Если оставить `DATABASE_MIGRATION_URL` пустым, работа идет с одной ролью, а `DATABASE_URL` выполняет обе задачи точно так же, как до разделения. Это поддерживаемая конфигурация, а не устаревшая. Она подходит для управляемого Postgres, где создание ролей часто не в вашей власти.

### Внешний и управляемый Postgres {#external-and-managed-postgres}

В RDS, Supabase, Cloud SQL или любом кластере, который вы запускаете сами, разделение включается по желанию. Создайте роль времени выполнения один раз:

```sql
CREATE ROLE snapotter_app LOGIN PASSWORD 'choose-a-strong-password'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS;
```

Затем передайте SnapOtter обе строки подключения, указывающие на один и тот же хост, порт и базу данных:

```bash
DATABASE_URL=postgres://snapotter_app:choose-a-strong-password@db.example.com:5432/snapotter
DATABASE_MIGRATION_URL=postgres://snapotter:the-owner-password@db.example.com:5432/snapotter
```

На этом остановитесь. SnapOtter сам применяет права и повторно применяет их после каждой миграции, поэтому таблица, добавленная в будущем релизе, будет охвачена без запуска SQL для нее.

Роль в `DATABASE_MIGRATION_URL` должна быть владельцем таблиц SnapOtter, потому что выдавать права на таблицу может только ее владелец. В существующей установке это значит роль, под которой вы запускали SnapOtter, а не новая, созданная для этой цели. Если указать новую роль, которая ничем не владеет, загрузка завершится ошибкой, говорящей именно об этом. Ей также нужен `CREATEROLE` для создания и поддержки роли времени выполнения, а также право создавать схему `drizzle`.

Если указать одну и ту же роль в обоих URL, разделение отключено, и SnapOtter сообщает об этом в журнале, а не делает вид, что это не так. Если ваш провайдер не дает роль, которая может и владеть таблицами, и иметь `CREATEROLE`, работайте с одной ролью.

### Почему бит суперпользователя не трогают {#why-the-superuser-bit-is-left-alone}

SnapOtter никогда сам не снимает `SUPERUSER` с роли. В установке, созданной до разделения, `snapotter` является единственным суперпользователем кластера, и его понижение оставило бы кластер без суперпользователей, с возможностью восстановления только через однопользовательский режим при остановленном сервере. Защиту дает перенос долгоживущего подключения на ограниченную роль. Суперпользователь присутствует в соединении на несколько секунд загрузки, а затем исчезает.

Свежие установки «все в одном» никогда не сталкиваются с этой проблемой. В них три роли: `postgres` (суперпользователь начальной настройки, отсутствующий во всех строках подключения, которые использует SnapOtter), `snapotter` (`NOSUPERUSER`, владеет данными, подключается только при загрузке) и `snapotter_app` (только строки, обслуживает запросы).

Чтобы все же понизить более старую роль `snapotter`, сначала создайте второго суперпользователя и войдите под ним, чтобы убедиться, что он работает. Затем `ALTER ROLE snapotter NOSUPERUSER`.

## Резервное копирование и восстановление {#backup-and-restore}

Реляционная база данных находится в томе `SnapOtter-pgdata` контейнера Postgres, а не в томе `/data` приложения.

**Логическая резервная копия с проверкой (рекомендуется)**

```bash
# Dump into PostgreSQL's portable custom archive format
docker exec SnapOtter-postgres \
  pg_dump --format=custom --no-owner -U snapotter snapotter > snapotter.dump
test -s snapotter.dump
docker exec -i SnapOtter-postgres pg_restore --list < snapotter.dump >/dev/null

# Restore into a fresh/disposable target first and fail on the first SQL error
docker exec -i SnapOtter-postgres \
  pg_restore --exit-on-error --clean --if-exists --no-owner \
  -U snapotter -d snapotter < snapotter.dump
```

Обе команды подключаются как `snapotter`, владелец, и так и должно оставаться. Роль времени выполнения не видит схему `drizzle`, поэтому дамп, снятый под этой ролью, получился бы неполным. `--no-owner` оставляет восстановленные объекты во владении того, кто выполняет восстановление, поэтому запуск от владельца помещает владение туда, где его ожидают права. Одна оговорка для свежего кластера: `pg_dump` содержит права, но не роли, которые они называют, поэтому создайте `snapotter_app` до восстановления, иначе `--exit-on-error` остановится на первом `GRANT`. SnapOtter в любом случае повторно применит права при следующей загрузке.

Этот дамп базы данных не содержит сохраненных объектов библиотеки в `/data/files` и надежного состояния BullMQ в Redis. Резервное копирование и восстановление их выполняются по согласованной процедуре из раздела [Безопасность и защита](/ru/guide/security#backup-and-recovery).

**Холодный снимок тома**

```bash
# Stop every service first, then use your storage platform to snapshot the
# PostgreSQL, app-data, and Redis volumes as one crash-consistent set.
docker compose -f docker/docker-compose.yml stop
```

Не копируйте каталог данных работающего PostgreSQL с помощью `tar`. Compose добавляет к именам томов префикс проекта, поэтому определяйте идентификаторы смонтированных томов из `docker inspect` или вашей платформы хранения, а не считайте, что метка `SnapOtter-pgdata` записана буквально.

### Миграция с 1.x (SQLite) {#migrating-from-1-x-sqlite}

Обновление с SnapOtter 1.x описано в отдельном руководстве: см. [Обновление с 1.x до 2.0](./upgrading). Если коротко, используйте существующий том `/data`, и версия 2.0 автоматически обнаружит и импортирует `/data/snapotter.db` при первой загрузке (или задайте `SQLITE_MIGRATE_PATH`, чтобы указать на него явно). Сначала сделайте резервную копию всего тома `/data`, а не только `snapotter.db`: 1.x использует режим WAL в SQLite, поэтому в остановленном контейнере большая часть данных часто остается в `snapotter.db-wal` рядом с почти пустым `snapotter.db`.
