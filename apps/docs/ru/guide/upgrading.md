# Обновление с 1.x до 2.0 {#upgrading-from-1-x-to-2-0}

SnapOtter 1.x хранил всё в одном файле SQLite и работал как один контейнер. SnapOtter 2.0 использует PostgreSQL и Redis. Это руководство описывает перенос установки 1.x на 2.0 без потери данных.

Коротко: используйте существующий том `/data`, и 2.0 автоматически импортирует вашу базу данных 1.x при первой загрузке. Ваши пользователи, сохранённые файлы, настройки, ключи API и конвейеры переносятся. Старая база данных никогда не изменяется, поэтому вы всегда можете откатиться.

::: tip Заметка для пользователей 1.x
Многие из вас доверяли SnapOtter с первого дня, и ваши отзывы сформировали этот выпуск. В 2.0 многое изменилось под капотом, и это руководство создано для того, чтобы переход не стоил вам ничего важного. Ваши учётные записи, файлы, настройки, ключи API и конвейеры переносятся, а старая база данных остаётся нетронутой. Спасибо, что обновляетесь вместе с нами.
:::

## Перед началом: сделайте резервную копию всего тома `/data` {#before-you-start-back-up-the-whole-data-volume}

Делайте это в первую очередь и каждый раз. Копируйте **весь** том `/data`, а не только файл `snapotter.db`.

Вот почему это важно. 1.x запускает SQLite в режиме WAL, поэтому остановленный контейнер 1.x обычно оставляет большую часть зафиксированных данных в `snapotter.db-wal` рядом с почти пустым `snapotter.db`. Если скопировать только `snapotter.db`, вы получите пустую базу данных и незаметно потеряете всё. Том содержит `snapotter.db`, `snapotter.db-wal`, `snapotter.db-shm` и ваш каталог `files/` вместе, и их нужно переносить как единый набор.

```bash
# Adjust the volume name to match yours (see "Check your volume name" below).
docker run --rm -v SnapOtter-data:/data -v "$PWD":/backup \
  alpine tar czf /backup/snapotter-1x-data.tgz -C /data .
```

## Сначала обновитесь до 1.17.2 {#upgrade-to-1-17-2-first}

Перед переходом на 2.0 обновите установку 1.x до последнего выпуска 1.x (1.17.2). Тогда 1.x выполнит собственные финальные миграции схемы, и 2.0 будет импортировать данные из известной, полной схемы. Обновление со старой версии 1.x сразу до 2.0 не поддерживается.

## Проверьте имя тома {#check-your-volume-name}

Импортёр видит ваши данные, только если стек 2.0 монтирует тот же том, который использовала установка 1.x. Имена томов Docker чувствительны к регистру, а в старых фрагментах README использовалось имя в нижнем регистре `snapotter-data`, тогда как в файлах Compose используется `SnapOtter-data`. Проверьте, какое у вас:

```bash
docker volume ls | grep -i snapotter
```

Используйте именно это имя в конфигурации 2.0.

## Вариант A: один контейнер (быстрее всего) {#path-a-single-container-quickest}

Если вы запускаете SnapOtter одним `docker run`, продолжайте так же. 2.0 поднимает встроенные PostgreSQL и Redis внутри контейнера, если вы не задаёте `DATABASE_URL` или `REDIS_URL`, а также автоматически находит и импортирует `/data/snapotter.db` при первой загрузке.

```bash
docker run -d --name snapotter -p 1349:1349 \
  -v SnapOtter-data:/data \
  snapotter/snapotter:latest
```

Следите в журналах за строкой вроде:

```
Imported 1.x SQLite database: {"tables":{"users":2,"teams":1,...},"blobs":{"present":1,"missing":0}}
```

Это всё. Входите с прежними учётными данными.

## Вариант B: Compose (рекомендуется для продакшена) {#path-b-compose-recommended-for-production}

Стек Compose 2.0 запускает три сервиса (приложение, Postgres, Redis). Используйте том `/data` из 1.x для сервиса приложения. Приложение автоматически находит `/data/snapotter.db` и импортирует его в Postgres при первой загрузке.

```yaml
services:
  SnapOtter:
    image: snapotter/snapotter:latest
    volumes:
      - SnapOtter-data:/data          # your existing 1.x volume
      - SnapOtter-workspace:/tmp/workspace
    environment:
      - DATABASE_URL=postgres://${POSTGRES_APP_USER:-snapotter_app}:${POSTGRES_APP_PASSWORD:-snapotter_app}@postgres:5432/${POSTGRES_DB:-snapotter}
      - DATABASE_MIGRATION_URL=postgres://${POSTGRES_USER:-snapotter}:${POSTGRES_PASSWORD:-snapotter}@postgres:5432/${POSTGRES_DB:-snapotter}
      - REDIS_URL=redis://:snapotter@redis:6379
    # ...
```

Если вы предпочитаете явно указать старую базу данных, задайте `SQLITE_MIGRATE_PATH=/data/snapotter.db`. Явный путь всегда имеет приоритет над автоопределением.

## Предварительный просмотр импорта (необязательно) {#preview-the-import-first-optional}

Чтобы увидеть, что именно будет импортировано, ничего не записывая, выполните пробный запуск для файла вашей базы данных:

```bash
pnpm --filter @snapotter/api migrate:sqlite -- /path/to/snapotter.db --dry-run
```

Он выводит число строк по таблицам, сколько файлов сохранённой библиотеки найдено на диске и какие статусы задач будут нормализованы. Работающий Postgres для этого не нужен.

## Что переносится, а что нет {#what-carries-over-and-what-does-not}

Переносится:

- Пользователи и возможность входа. Хеши паролей не меняются, поэтому прежние имя пользователя и пароль работают.
- Команды, настройки (включая идентичность вашего экземпляра), роли, ключи API (они продолжают работать) и сохранённые конвейеры.
- Записи истории задач.
- Ваша библиотека сохранённых файлов, как записи, так и сами файлы, потому что `/data/files` сохраняется на томе.

Не переносится:

- Сессии входа. После обновления каждый входит один раз. Учётные данные не меняются, так что это единственный повторный вход и ничего больше.
- Входные и выходные файлы старых задач обработки. Они находились во временном рабочем пространстве и по замыслу удалены. Записи истории задач остаются.
- Флаги согласия на аналитику для отдельных пользователей из 1.x, у которых нет аналога в 2.0 (аналитика в 2.0 настраивается на уровне экземпляра).

## Отключение импорта {#turning-the-import-off}

Если вы намеренно хотите получить чистую базу данных, даже когда на томе есть `snapotter.db`, задайте `SQLITE_MIGRATE_PATH=off`.

## Если в экземпляре 2.0 уже есть данные {#if-you-already-have-data-in-the-2-0-instance}

Импортёр работает только с пустой базой данных. Если вы запустили 2.0 с нуля (создав данные), а затем смонтировали старый `snapotter.db`, 2.0 обнаружит его, но импортировать не станет, потому что слияние двух наборов данных может вызвать конфликты идентификаторов. В журналах появится предупреждение. Чтобы импортировать данные 1.x, нужен пустой экземпляр:

- Если экземпляр 2.0 содержит только администратора по умолчанию (вы по-настоящему им не пользовались), остановите стек, удалите том Postgres (`SnapOtter-pgdata`) и снова запустите с имеющимся старым `/data`. Импорт пройдёт чисто. Это сотрёт только временные данные Postgres, а не вашу базу данных 1.x.
- Если экземпляр 2.0 содержит реальные данные, которые вы хотите сохранить, два набора данных нельзя объединить автоматически. Экспортируйте нужное и импортируйте данные 1.x в отдельное новое развёртывание.

## Откат {#rolling-back}

Обновление никогда не изменяет и не удаляет ваш `snapotter.db` из 1.x. Если нужно вернуться на 1.x, разверните образ 1.x с тем же томом. Всё, что вы создали в 2.0 после обновления, хранится в Postgres и не окажется в базе данных 1.x, поэтому при необходимости откатывайтесь без промедления.
