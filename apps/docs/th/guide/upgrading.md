# การอัปเกรดจาก 1.x เป็น 2.0 {#upgrading-from-1-x-to-2-0}

SnapOtter 1.x เก็บทุกอย่างไว้ในไฟล์ SQLite ไฟล์เดียวและรันเป็นคอนเทนเนอร์เดียว SnapOtter 2.0 ใช้ PostgreSQL และ Redis คู่มือนี้พาคุณย้ายการติดตั้ง 1.x ไปเป็น 2.0 โดยไม่สูญเสียข้อมูล

สรุปสั้น ๆ คือใช้วอลุ่ม `/data` เดิมของคุณ แล้ว 2.0 จะนำเข้าฐานข้อมูล 1.x ให้อัตโนมัติเมื่อบูตครั้งแรก ผู้ใช้ ไฟล์ที่บันทึกไว้ การตั้งค่า คีย์ API และไปป์ไลน์ของคุณจะย้ายมาครบ ฐานข้อมูลเดิมจะไม่ถูกแก้ไขเลย คุณจึงย้อนกลับได้เสมอ

::: tip ข้อความถึงผู้ใช้ 1.x ของเรา
พวกคุณหลายคนไว้วางใจ SnapOtter ตั้งแต่วันแรก และความคิดเห็นของคุณช่วยหล่อหลอมรุ่นนี้ 2.0 เปลี่ยนแปลงภายในไปมาก และคู่มือนี้มีไว้เพื่อให้การย้ายไม่ทำให้คุณสูญเสียสิ่งที่คุณใส่ใจ บัญชี ไฟล์ การตั้งค่า คีย์ API และไปป์ไลน์ของคุณย้ายมาด้วย และฐานข้อมูลเดิมของคุณจะไม่ถูกแตะต้อง ขอบคุณที่อัปเกรดไปกับเรา
:::

## ก่อนเริ่ม: สำรองวอลุ่ม `/data` ทั้งหมด {#before-you-start-back-up-the-whole-data-volume}

ทำสิ่งนี้ก่อนเสมอ ทุกครั้ง สำรองวอลุ่ม `/data` **ทั้งหมด** ไม่ใช่แค่ไฟล์ `snapotter.db`

เหตุผลที่สำคัญคือ 1.x รัน SQLite ในโหมด WAL คอนเทนเนอร์ 1.x ที่หยุดทำงานแล้วจึงมักทิ้งข้อมูลที่คอมมิตแล้วส่วนใหญ่ไว้ใน `snapotter.db-wal` ข้างไฟล์ `snapotter.db` ที่แทบว่างเปล่า การคัดลอกเฉพาะ `snapotter.db` จะได้ฐานข้อมูลว่างและสูญเสียทุกอย่างโดยไม่มีการแจ้งเตือน วอลุ่มนี้มี `snapotter.db`, `snapotter.db-wal`, `snapotter.db-shm` และไดเรกทอรี `files/` ของคุณอยู่ด้วยกัน และต้องย้ายไปเป็นชุดเดียวกัน

```bash
# Adjust the volume name to match yours (see "Check your volume name" below).
docker run --rm -v SnapOtter-data:/data -v "$PWD":/backup \
  alpine tar czf /backup/snapotter-1x-data.tgz -C /data .
```

## อัปเกรดเป็น 1.17.2 ก่อน {#upgrade-to-1-17-2-first}

อัปเกรดการติดตั้ง 1.x ของคุณเป็นรุ่น 1.x ล่าสุด (1.17.2) ก่อนย้ายไป 2.0 เพื่อให้ 1.x รันการย้ายสคีมาครั้งสุดท้ายของตัวเอง 2.0 จึงนำเข้าจากสคีมาที่สมบูรณ์และทราบแน่ชัด ไม่รองรับการอัปเกรดจาก 1.x รุ่นเก่ากว่านั้นไป 2.0 โดยตรง

## ตรวจสอบชื่อวอลุ่มของคุณ {#check-your-volume-name}

ตัวนำเข้าจะเห็นข้อมูลของคุณก็ต่อเมื่อสแต็ก 2.0 เมานต์วอลุ่มเดียวกับที่การติดตั้ง 1.x ใช้ ชื่อวอลุ่ม Docker คำนึงถึงตัวพิมพ์ใหญ่เล็ก และตัวอย่างใน README รุ่นเก่าใช้ `snapotter-data` ตัวพิมพ์เล็ก ขณะที่ไฟล์ Compose ใช้ `SnapOtter-data` ยืนยันว่าคุณใช้ชื่อไหน:

```bash
docker volume ls | grep -i snapotter
```

ใช้ชื่อที่ตรงกันนั้นในการกำหนดค่า 2.0 ของคุณ

## เส้นทาง A: คอนเทนเนอร์เดี่ยว (เร็วที่สุด) {#path-a-single-container-quickest}

หากคุณรัน SnapOtter ด้วย `docker run` เดียว ก็ทำต่อไปอย่างนั้น 2.0 จะบูต PostgreSQL และ Redis แบบฝังในตัวภายในคอนเทนเนอร์เมื่อคุณไม่ได้ตั้งค่า `DATABASE_URL` หรือ `REDIS_URL` และจะตรวจหาและนำเข้า `/data/snapotter.db` โดยอัตโนมัติเมื่อบูตครั้งแรก

```bash
docker run -d --name snapotter -p 1349:1349 \
  -v SnapOtter-data:/data \
  snapotter/snapotter:latest
```

ดูในบันทึกว่ามีบรรทัดลักษณะนี้หรือไม่:

```
Imported 1.x SQLite database: {"tables":{"users":2,"teams":1,...},"blobs":{"present":1,"missing":0}}
```

เสร็จเรียบร้อย เข้าสู่ระบบด้วยข้อมูลประจำตัวเดิมของคุณได้เลย

## เส้นทาง B: Compose (แนะนำสำหรับการใช้งานจริง) {#path-b-compose-recommended-for-production}

สแต็ก Compose ของ 2.0 รันสามบริการ (แอป, Postgres, Redis) ใช้วอลุ่ม `/data` ของ 1.x เดิมสำหรับบริการแอป แอปจะตรวจหา `/data/snapotter.db` โดยอัตโนมัติและนำเข้าสู่ Postgres เมื่อบูตครั้งแรก

```yaml
services:
  SnapOtter:
    image: snapotter/snapotter:latest
    volumes:
      - SnapOtter-data:/data          # your existing 1.x volume
      - SnapOtter-workspace:/tmp/workspace
    environment:
      - DATABASE_URL=postgres://${POSTGRES_APP_USER:-snapotter_app}:${POSTGRES_APP_PASSWORD:-snapotter_app}@postgres:5432/${POSTGRES_DB:-snapotter}
      - DATABASE_MIGRATION_URL=postgres://${POSTGRES_USER:-snapotter}:${POSTGRES_PASSWORD:-snapotter}@postgres:5432/${POSTGRES_DB:-snapotter}
      - REDIS_URL=redis://:snapotter@redis:6379
    # ...
```

หากต้องการชี้ไปยังฐานข้อมูลเดิมอย่างชัดเจน ให้ตั้งค่า `SQLITE_MIGRATE_PATH=/data/snapotter.db` เส้นทางที่ระบุชัดเจนจะมีผลเหนือการตรวจหาอัตโนมัติเสมอ

## ดูตัวอย่างการนำเข้าก่อน (ไม่บังคับ) {#preview-the-import-first-optional}

หากต้องการดูว่าจะนำเข้าอะไรบ้างโดยไม่เขียนข้อมูลใด ๆ ให้รัน dry run กับไฟล์ฐานข้อมูลของคุณ:

```bash
pnpm --filter @snapotter/api migrate:sqlite -- /path/to/snapotter.db --dry-run
```

คำสั่งนี้จะแสดงจำนวนแถวต่อตาราง จำนวนไฟล์ในคลังที่บันทึกไว้ซึ่งพบบนดิสก์ และสถานะงานที่จะถูกปรับให้เป็นมาตรฐาน คำสั่งนี้ไม่ต้องใช้ Postgres ที่กำลังทำงาน

## สิ่งที่ย้ายมา และสิ่งที่ไม่ย้ายมา {#what-carries-over-and-what-does-not}

สิ่งที่ย้ายมา:

- ผู้ใช้ และความสามารถในการเข้าสู่ระบบ แฮชรหัสผ่านไม่เปลี่ยนแปลง ดังนั้นชื่อผู้ใช้และรหัสผ่านเดิมใช้ได้
- ทีม การตั้งค่า (รวมถึงตัวตนของอินสแตนซ์) บทบาท คีย์ API (ใช้งานต่อได้) และไปป์ไลน์ที่บันทึกไว้
- บันทึกประวัติงาน
- คลังไฟล์ที่บันทึกไว้ของคุณ ทั้งระเบียนและไฟล์จริง เพราะ `/data/files` ถูกเก็บรักษาไว้บนวอลุ่ม

สิ่งที่ไม่ย้ายมา:

- เซสชันการเข้าสู่ระบบ ทุกคนต้องเข้าสู่ระบบอีกครั้งหนึ่งครั้งหลังอัปเกรด ข้อมูลประจำตัวไม่เปลี่ยนแปลง จึงเป็นการเข้าสู่ระบบใหม่เพียงครั้งเดียวเท่านั้น
- ไฟล์อินพุตและเอาต์พุตของงานประมวลผลเก่า ไฟล์เหล่านั้นอยู่ในเวิร์กสเปซชั่วคราวและหายไปตามการออกแบบ บันทึกประวัติงานยังคงอยู่
- แฟล็กความยินยอมด้านการวิเคราะห์รายผู้ใช้จาก 1.x ซึ่งไม่มีสิ่งที่เทียบเท่าใน 2.0 (การวิเคราะห์ใน 2.0 เป็นการตั้งค่าระดับอินสแตนซ์)

## การปิดการนำเข้า {#turning-the-import-off}

หากคุณตั้งใจต้องการฐานข้อมูลใหม่ทั้งที่มี `snapotter.db` อยู่บนวอลุ่ม ให้ตั้งค่า `SQLITE_MIGRATE_PATH=off`

## หากคุณมีข้อมูลในอินสแตนซ์ 2.0 อยู่แล้ว {#if-you-already-have-data-in-the-2-0-instance}

ตัวนำเข้าจะทำงานกับฐานข้อมูลที่ว่างเท่านั้น หากคุณเริ่ม 2.0 ใหม่ (สร้างข้อมูลไปแล้ว) แล้วภายหลังเมานต์ `snapotter.db` เดิม 2.0 จะตรวจพบแต่จะไม่นำเข้า เพราะการรวมชุดข้อมูลสองชุดอาจทำให้ ID ชนกัน คุณจะเห็นคำเตือนในบันทึก หากต้องการนำเข้าข้อมูล 1.x คุณต้องมีอินสแตนซ์ที่ว่างเปล่า:

- หากอินสแตนซ์ 2.0 มีเพียงผู้ดูแลระบบเริ่มต้น (คุณยังไม่ได้ใช้งานจริง) ให้หยุดสแต็ก ลบวอลุ่ม Postgres (`SnapOtter-pgdata`) แล้วบูตอีกครั้งโดยมี `/data` เดิมอยู่ มันจะนำเข้าได้อย่างสะอาด วิธีนี้ลบเฉพาะข้อมูล Postgres ชั่วคราว ไม่ลบฐานข้อมูล 1.x ของคุณ
- หากอินสแตนซ์ 2.0 มีข้อมูลจริงที่คุณต้องการเก็บไว้ ชุดข้อมูลทั้งสองจะรวมกันอัตโนมัติไม่ได้ ให้ส่งออกสิ่งที่ต้องการ แล้วนำเข้าข้อมูล 1.x ไปยังการติดตั้งใหม่แยกต่างหาก

## การย้อนกลับ {#rolling-back}

การอัปเกรดจะไม่แก้ไขหรือลบ `snapotter.db` ของ 1.x ของคุณ หากต้องการกลับไปใช้ 1.x ให้ติดตั้งอิมเมจ 1.x ใหม่กับวอลุ่มเดิม สิ่งที่คุณสร้างใน 2.0 หลังการอัปเกรดอยู่ใน Postgres และจะไม่อยู่ในฐานข้อมูล 1.x ดังนั้นหากคิดจะย้อนกลับ ให้ทำโดยเร็ว
